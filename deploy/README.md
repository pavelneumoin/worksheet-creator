# Публичный запуск ЛистОК

Проверенная локально основа: 2 vCPU, 4 ГиБ памяти; для Docker и TeX выделяем SSD 30 ГиБ.
Ресурсы и стоимость провайдера проверяются отдельно перед созданием сервера.
Вход публичного приложения — только MAX. Локальный режим для сервера не подходит.

## Размещение

1. Для новой Ubuntu 24.04 используйте `cloud-init.example.yaml`, подставив публичный
   SSH-ключ администратора. Он устанавливает Docker и Compose из репозитория Ubuntu.
   Приватный ключ и токены провайдеров в метаданные ВМ не помещаются.
2. Получите исходники нужного коммита и войдите в корень репозитория.
3. Создайте серверный `.env` по `.env.example`: токены остаются на сервере.
   `MAX_APP_URL=https://ваш-домен` — корневой адрес без пути, query и fragment.
4. Направьте DNS A-запись домена на публичный IP сервера. Откройте TCP 80/443.
   SSH разрешите только администратору по ключу; порт 3005 остаётся на loopback.
5. Поместите набор стандартных и официальных российских CA в `.local-certs/gigachat-ca.pem`.
   Для существующего окружения: `python scripts/check_deployment.py` проверяет настройки
   без сетевых запросов и без вывода секретов.
6. Соберите и запустите:

Команды Docker ниже выполняются администратором; если текущий пользователь не входит
в группу `docker`, добавляйте `sudo`. Не предоставляйте группе `docker` доступ обычных
пользователей приложения.

```bash
docker compose -f compose.yaml -f compose.https.yaml config --quiet
docker compose -f compose.yaml -f compose.https.yaml up --build -d --wait --wait-timeout 180
curl --fail https://ваш-домен/api/health/ready
docker compose exec -T listok python scripts/check_connections.py --max --gigachat
```

Caddy автоматически получает и продлевает HTTPS-сертификат; его состояние сохраняется
в отдельных томах. Конфигурация проверяется в CI. Access-лог не включён, поскольку
временные ссылки скачивания содержат разрешение на доступ к файлу.
[Автоматический HTTPS Caddy](https://caddyserver.com/docs/automatic-https).

`/api/status` проверяет живой веб-процесс. `/api/health/ready` возвращает 503, если
пропал обработчик ИИ, компилятор или его обработчик. Это отдельные проверки:
веб-сервис должен подняться до запуска обработчиков.

## Приёмка

- Записать тот же `MAX_APP_URL` в настройках мини-приложения бота.
- Открыть приложение в MAX, проверить настоящий подписанный вход, фото, правку,
  PDF и ответы, повторное открытие, классы и отчёт. Повторить со вторым профилем.
- В MAX приватные ссылки готовятся до нажатия. Если ссылка истекла или ещё грузится,
  приложение просит нажать ещё раз после подготовки — вызов Bridge остаётся в обработчике клика.
  [Требования MAX к скачиванию](https://dev.max.ru/docs/webapps/bridge/).
- Проверить 401 на `/api/v2/materials` без входа и отсутствие локального входа.
- Перезапустить сервисы, убедиться, что материалы и отчёты сохранены.
- Создать копию и выполнить контроль восстановления в отдельной папке.

## Копирование и обновление

```bash
docker compose exec -T listok python scripts/manage_storage.py backup /app/data/pre-update.zip
docker compose cp listok:/app/data/pre-update.zip ./pre-update.zip
```

Перенесите архив в защищённое хранилище вне сервера. Он содержит приватные данные.
Используйте новое имя при каждой копии. Для восстановления скопируйте архив на машину
с установленными зависимостями и выполните `python scripts/manage_storage.py restore архив.zip новая-папка`.
Не восстанавливайте поверх рабочей базы. При восстановлении сессии отзываются,
незавершённые платные запросы не повторяются автоматически.

Обновление выполняется после копии: загрузить проверенный коммит, повторить `up --build`.
Не использовать `docker compose down -v`: это удаляет постоянные данные.
Перед сменой схемы хранения убедиться в совместимости отката.
